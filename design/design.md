多周期减脂计划管理系统
（Fat Loss Planner）设计开发文档（Functional Design）
一、系统目标

本系统用于帮助用户制定并执行减脂计划，通过每日饮食与运动记录，持续评估用户是否达到目标热量缺口，并以日历形式进行可视化反馈，从而形成可持续执行的行为闭环。
允许用户注册然后登录，制作/跟踪/查看自己的减脂计划

系统重点不在于简单记录数据，而在于：

明确每日目标；

持续反馈执行情况；

可视化长期趋势；

判断阶段目标是否可达成。

二、核心设计原则
2.1 行为驱动优先

系统核心关注：

用户今天是否完成目标。

而不是：

用户记录了多少数据。

所有功能围绕：

达标判断；

执行反馈；

计划进度。

展开。

2.2 低认知负担

用户每天记录时间应控制在：

≤1分钟。

避免：

手动计算热量；

复杂填写。

系统负责：

自动计算；

自动判断。

2.3 长周期可坚持

减脂周期通常为：

60～120天。

系统需支持：

长时间持续使用；

快速查看历史执行质量。

三、系统功能模块总览

系统分为以下核心模块：

1）减脂计划生成模块（Plan Generator）

首次使用或创建新计划时使用。

2）减脂执行日历模块（Execution Calendar）

系统核心界面。

3）每日记录模块（Daily Log）

饮食与运动输入入口。

4）计划进度与预测模块（Progress & Forecast）

顶部信息区域。

5）统计与趋势模块（Analytics）

长期执行情况展示。

四、减脂计划生成模块
4.1 功能目标

帮助用户生成科学合理的减脂周期目标。

系统负责：

基础代谢估算；

每日目标摄入计算；

周期日历生成。

4.2 用户输入信息

**原则：优先让用户选择而非输入文本，以降低使用难度并便于系统计算。**

首次进入需引导用户通过**选择项**完成信息录入：

基础信息：

性别（单选：男/女）；

年龄（年龄段或数字选择器）；

身高（区间选择或滑块）；

当前体重（区间选择或数字输入，可后续在日历中随时更新）；

目标体重（区间选择或数字输入）。

生活方式：

工作性质（单选：久坐/站立/体力）；

平均每日步数（档位选择，如 少于3000 / 3000～6000 / 6000～10000 / 超过10000）；

通勤方式（单选：无/步行/骑车/公交/开车等）。

运动习惯：

每周运动次数（档位选择）；

每次运动时长（档位选择）；

运动类型（多选预设：跑步/力量/游泳/骑行等）。

健康因素（可选）：

睡眠情况（档位选择）；

健康备注（可选简短文本）。

避免自由文本输入，仅在必要时保留少量填空。

4.3 系统计算内容

系统生成：

基础代谢；

日常消耗；

每日目标摄入；

推荐每日热量缺口。

并输出：

每日摄入目标：

≤ XXXX kcal。
4.4 计划周期生成

根据：

当前体重；

目标体重；

用户期望时间。

生成：

开始日期 — 结束日期。

系统生成对应：

每日执行日历。

4.5 用户确认阶段

展示：

是否现实；

是否过快。

例如：

预计每周下降：

0.5kg。

允许用户确认或修改。

十二、开发技术栈
部署平台：netlify
开发语言：vue+js
数据库：Netlify DB

12.1 数据库能力边界（实现前确认）

本系统需要支持：

多表关联查询（User/Plan/DailyLog/WeightLog）；

按 user_id 的严格数据隔离查询；

按日期范围统计与分页查询；

唯一约束（如 plan_id + date）与必要索引。

若 Netlify DB 在关系查询、索引或事务能力上无法满足以上需求，
建议在 MVP 初期即切换为托管 Postgres，避免中后期重构成本。

十四、计算规范（Calculation Specification）
14.1 BMR 公式

采用：

Mifflin-St Jeor

男性：

BMR =
10×体重 +
6.25×身高 -
5×年龄 +5

女性：

BMR =
10×体重 +
6.25×身高 -
5×年龄 -161
14.2 活动系数（Activity Factor）

统一表：

类型	系数
久坐	1.2
轻度活动	1.3
中度	1.45
高活动	1.6

计算：

TDEE =
BMR × ActivityFactor
+ 平均每日运动消耗。
14.3 最小摄入下限

避免极端节食。

男性：

≥1200 kcal。

女性：

≥1000 kcal。

若用户设置低于：

系统警告。

14.4 目标缺口上下限

每日推荐：

300 ~ 700 kcal。

规则：

<300 → 减脂效率过低。

>700 → 提示偏激进。

>=900 → 标记为风险（强警告，可限制继续下发该目标）。

系统提示。

十五、预测规范（Forecast Specification）
15.1 使用最近 N 天

默认：

N = 14 天。

原因：

足够平滑；

避免短期波动。

15.2 缺失值处理

若某天无记录：

跳过。

不参与预测。

连续：

≥5天缺失。

暂停预测。

15.3 异常体重过滤

忽略：

单日变化 >2kg。

例如：

75kg → 72kg。

通常为：

饮水；

输入错误。

过滤策略：

Median Filter。

或简单：

±2kg discard。
十六、体重记录规则
16.1 同日多次记录

统一：

⭐ 最后一次为准。

例如：

07:30 76kg
21:00 75.6kg

采用：

75.6kg。

理由：

用户晚间补录常见；

避免复杂平均。

16.2 推荐提示

UI 提示：

建议早晨空腹称重。

但不强制。

十八、状态重算机制

（非常关键。）

18.1 触发点

以下行为触发：

DailyLog 修改：

修改食物；

删除运动。

触发：

当天 deficit 重算。
WeightLog 修改：

触发：

趋势预测重算。
Plan 修改：

例如：

改目标体重。

触发：

全部历史重算。
18.2 重算范围

避免全量。

建议：

仅未来预测 + 最近30天。
十九、认证与权限
19.1 注册登录

支持：

6位数字账号 + Password。

MVP 不做复杂 OAuth 与邮箱强绑定。

账号规则：

仅允许 000000~999999 的 6 位数字；

必须全局唯一；

建议屏蔽弱账号（如 000000、123456、111111）。

19.2 会话策略

推荐：

Token Session。

有效期：

7 天。

支持自动续期。

19.3 登录安全策略（方案A必需）

为防止账号枚举与撞库，MVP 至少实现：

按 IP + account_id 双维度限流；

连续失败 5 次，账号锁定 15 分钟；

统一错误提示（不区分“账号不存在”或“密码错误”）；

记录登录失败与解锁审计日志。

19.4 数据隔离

所有查询：

必须：

WHERE user_id = session_user。

禁止跨用户访问。
